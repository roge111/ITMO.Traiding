# ADR-003: Отдельный Go-сервис для инжестии котировок

#docs #adr #go

**Статус:** Принято  
**Дата:** 2024  
**Участники:** Команда ITMO.Trading

---

## Контекст

Kernel module генерирует котировки через `/dev/itmo_quotes` — символьный misc device. Данные нужно читать из устройства и записывать в ClickHouse.

Kotlin/Ktor Gateway уже является центральным компонентом системы и имеет соединение с ClickHouse для чтения.

## Проблема

Где реализовать логику чтения `/dev/itmo_quotes` и записи в ClickHouse — в существующем Ktor Gateway или в отдельном сервисе?

## Рассмотренные варианты

### Вариант A: Логика инжестии внутри Ktor Gateway
- **+** Один сервис, проще деплой
- **+** Общее соединение с ClickHouse
- **−** `/dev/itmo_quotes` — Linux device file; Ktor работает на JVM, которая не предназначена для работы с символьными устройствами напрямую
- **−** JVM overhead для высокочастотного polling (каждую секунду)
- **−** Mixing of concerns: HTTP API + device I/O в одном процессе
- **−** JVM-процесс, запущенный не под root, может не иметь доступа к `/dev/`

### Вариант B: Отдельный Go-сервис ✓
- **+** Go нативно работает с файлами устройств через `os.Open`
- **+** Низкий overhead для polling-цикла
- **+** Чёткое разделение ответственности: Gateway = HTTP API, Go = I/O pipeline
- **+** ClickHouse-go/v2 — высокопроизводительный native protocol клиент (port 9000)
- **−** Дополнительный сервис для запуска и мониторинга

### Вариант C: C-программа (userspace)
- **+** Максимальная близость к kernel module
- **−** Нужно реализовывать ClickHouse client на C — избыточная сложность
- **−** Ручное управление памятью

## Решение

**Принят вариант B.** Создан отдельный Go-сервис в `server/go/main.go`.

Ключевые характеристики:
- Polling каждую секунду через `os.Open` / `os.Close`
- In-memory дедупликация через `seen map[string]string`
- Native ClickHouse protocol через `clickhouse-go/v2` (port 9000, быстрее чем HTTP)
- Graceful shutdown через `context.WithCancel` + `os.Signal`

## Последствия

**Положительные:**
- Go-сервис запускается независимо от Gateway — можно перезапускать по отдельности
- Дедупликация на уровне Go снижает нагрузку на ClickHouse
- Native protocol (9000) быстрее, чем HTTP (8123, используемый Gateway)

**Отрицательные:**
- Два сервиса нужно запускать и мониторить отдельно
- `seen` map сбрасывается при перезапуске — первые несколько секунд после рестарта все котировки будут записаны заново
- Go-сервис не имеет HTTP API для health check (нет `/health` endpoint)
